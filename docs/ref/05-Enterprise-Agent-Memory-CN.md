# 企业级 Agent Memory：当"我是谁"变成"我在处理哪个案件"

[Extension: com.atlassian.confluence.macro.core/toc]
> 前四篇讲的是 AI 应该如何记忆。这一篇要问：**当 AI 面对的不是一个用户，而是成千上万个案件时，记忆系统该怎么变？**

---

## 前四篇的隐含假设

回头看我们讨论过的四个记忆系统——Letta 的四层架构、LangMem 的知识蒸馏引擎、Claude-Mem 的观察压缩、以及我们的统一分层模型——它们有一个共同的假设，根本到几乎看不见：

**一个 Agent，一个用户，一段持续的关系。**

Core Memory 存的是"用户叫张三"。Message Buffer 追踪的是"我们的对话"。Archival Memory 保存的是"我们讨论过的一切"。整个架构假设的是一个 AI 和一个人之间的单一、持续的对话线。

现在想象一个保险理赔 Agent。周一上午处理案件 #1234——张三的车祸理赔。周一下午，案件 #5678——李四的医疗险理赔。周二，张三打来更新情况。周三，三个新案件同时进来。

问题不再是"我在跟谁聊天"，而是 **"我现在在处理哪个案件？我对它了解多少？"**

这个转变以一种非常具体的方式打破了原来的四层模型：**L1（Core Memory）不能再是"始终钉在 prompt 里"了。** 你不可能把 5000 个案件的 Profile 同时塞进 prompt。Core Memory 没有消失——它变成了按 case_id 按需加载的东西。

一旦接受这一点，整个记忆架构都需要重新思考。

---

## 从"分层"到"分层 × 分域"

第四篇给出的统一模型有四层：

```
L1: 身份与画像       （始终可见，精确查找）
L2: 演化中的知识     （按需检索，语义搜索）
L3: 会话上下文       （自动管理，滚动压缩）
L4: 情景档案         （海量存储，渐进式披露）

```

这四层依然有效。但在企业级 Agent 中，每一层都需要第二个维度：**这条记忆属于谁？**

```
                    命名空间（属于谁？）
                    ┌──────────┬──────────┬──────────┐
                    │  Agent   │  Case    │  User    │
                    │ （共享） │（按案件）│（按用户）│
    ┌───────────────┼──────────┼──────────┼──────────┤
    │ L1: 画像      │ Agent    │ 案件     │ 用户     │
层  │               │ 身份     │ 事实     │ 偏好     │
    ├───────────────┼──────────┼──────────┼──────────┤
级  │ L2: 知识      │ 领域     │ 案件     │ 用户     │
    │               │ 知识     │ 历史     │ 历史     │
（  ├───────────────┼──────────┼──────────┼──────────┤
什  │ L3: 会话      │    —     │ 当前对话            │
么  │               │          │（共享上下文）        │
类  ├───────────────┼──────────┼──────────┼──────────┤
型  │ L4: 档案      │ 跨案件   │ 历史     │ 历史     │
）  │               │ 模式     │ 会话     │ 会话     │
    └───────────────┴──────────┴──────────┴──────────┘

```

这就是核心架构洞察：**企业级 Agent Memory = 层级 × 命名空间。** 层级定义信息的*类型*，命名空间定义信息*属于谁*。每条记忆都活在一个交叉点上。

下面逐一展开三个命名空间。

---

## 命名空间一：Case-Level —— 核心工作单元

在大多数企业 Agent 场景中——保险理赔、法律案件、客服工单、项目管理——**案件（case）** 是基本工作单位。每个案件有自己的身份、自己的事实、自己的历史。

### 案件画像（L1 × Case）

这个具体案件的结构化事实。等价于 Letta 的 Core Memory，但限定在单个案件范围，且按需加载而非永久钉在 prompt 里。

```
# Case #1234 画像
case_id: "CLM-1234"
type: "车险理赔"
status: "审核中"
policyholder: "张三"
policy_number: "POL-2024-56789"
incident_date: "2024-03-15"
incident_type: "与第三方碰撞"
claim_amount: 50000
assigned_adjuster: "王五"
key_dates:
  filed: "2024-03-16"
  docs_requested: "2024-03-17"
  next_followup: "2024-03-22"

```

这些数据来自两个来源——这个区分很重要：

**来源 A：已有数据库。** 上面这些字段是 DBA 设计的，结构化、经过验证、跨系统共享。Agent 可以读取，但通常不会直接回写。

**来源 B：AI 追加的记忆。** 在对话过程中，Agent 发现了现有数据库字段装不下的信息：

```
# Case #1234 — AI 追加的记忆（影子层）
context_notes:
  - "客户提到交警事故认定书下周才能拿到"
  - "客户情绪焦虑——已经打了 3 次电话催进度"
  - "客户偏好微信沟通，不喜欢接电话"
  - "第三方保险公司是太平洋保险，联系电话：400-xxx-xxxx"
  - "客户暗示如果月底前不解决，可能向银保监投诉"

```

这就是我所说的 **影子层（Shadow Layer）**：一个镜像并扩展数据库的记忆存储。数据库存的是系统设计时就预见到的字段。影子层存的是从真实对话中涌现出来的信息——混乱的、非结构化的，但往往至关重要的上下文，是任何 DBA 都无法预见的。

**为什么不直接往数据库加字段？** 因为你无法预测什么信息会重要。每个案件涌现出的信息都不同。"认定书延迟"不是标准字段。"偏好微信沟通"也不是。AI 记忆的全部意义就在于捕获刚性 schema 装不下的东西。

### 案件知识（L2 × Case）

关于这个具体案件的演化中的事实和发现，通过语义搜索按需检索：

```
Memory #1: [发现] 第三方司机的保险有 2 万元的责任上限。
           如果我方客户的维修费超过这个数，差额需要走我们的保单。

Memory #2: [决策] 与客户商定先去授权修理厂维修，不等第三方理赔结果。
           原因：客户通勤急需用车。

Memory #3: [更新] 交警认定书已于 2024-03-25 收到，确认第三方全责。
           认定书编号：JT-2024-03-1234。

```

这是案件版的 Letta Archival Memory。随着案件推进不断增长。和案件画像（存储当前状态）不同，案件知识存储的是**事实和决策的累积**——案件的故事。

### 案件会话记录（L4 × Case）

与该案件相关的每次交互的压缩记录：

```
{
  "session_id": "sess_078",
  "date": "2024-03-22",
  "participants": ["agent", "张三"],
  "channel": "微信",
  "summary": "客户来电查询理赔进度。告知交警认定书仍在等待中。客户表达不满——承诺周五前跟进。客户提到第三方司机一直不配合。",
  "action_items": ["周五前跟进客户", "联系第三方保险公司"],
  "mood": "frustrated"
}

```

这正是 Claude-Mem 的结构化观察方法大显身手的地方——每次交互都变成一条压缩的、可搜索的记录。

## 命名空间二：User-Level —— 跨案件的"人"

同一个用户可能在不同时间涉及多个案件。张三去年有一次车险理赔，今年问了房屋保险的事，下个月可能又来咨询旅行险。

User-level 记忆捕获的是关于这个**人**的信息，与他在讨论哪个案件无关。

### 用户画像（L1 × User）

```
# 用户：张三
user_id: "USR-ZS-001"
name: "张三"
preferred_name: "张哥"
contact_preference: "微信"
language: "中文"
communication_style: "直接型，要明确时间线，讨厌模糊回答"
sentiment_history: "超过 3 天没有更新就容易升级投诉"
relationship_tenure: "2021 年开始的客户，曾有 2 次理赔"

```

### 用户历史（L2 × User）

```
Memory #1: [历史] 2023 年有过一次房屋保险理赔（Case #0891）。
           30 天内解决，客户对处理过程满意。

Memory #2: [模式] 客户总是要求给出具体时间线。
           给范围（"2-4 周"）会让他不满。给确切日期效果好得多。

Memory #3: [备注] 客户提到过自己是律师。
           可能对合同细节和保单条款措辞更加敏感。

```

### 路由问题：Case vs User

当 Agent 从对话中提取信息时，必须判断：**这条信息属于案件还是属于用户？**

```
"交警认定书下周才能拿到"
    → Case-level（特定于这起事故）

"我习惯用微信沟通，不喜欢接电话"
    → User-level（所有未来交互都适用）

"3月25号到30号我出差，别给我打电话"
    → 两者都有？Case-level（影响这个案件的时间线）
                + User-level（短期内有用）

```

这个路由决策需要 LLM 来做，并且**需要你为你的领域定义明确的规则**：

```
ROUTING_GUIDELINES = """
对每条信息进行分类：

CASE-LEVEL（存到 case_id 下）：
- 关于事故的事实（发生了什么、什么时候、在哪里）
- 文件状态（已收到、待提交、缺失）
- 针对这个具体理赔做出的决策
- 特定于此案件的截止日期和承诺

USER-LEVEL（存到 user_id 下）：
- 沟通偏好（渠道、风格、时间）
- 影响未来交互的个人特征
- 关系历史和过往案件
- 影响沟通方式的职业背景

BOTH（两边都存）：
- 临时的可用性/日程安排（现在相关但不会永久有效）
"""

```

这就是你说的"专用设计"的核心所在。保险 vs 法律 vs 项目管理的路由规则完全不同。**命名空间抽象是通用的，路由逻辑是垂类的。**

## 命名空间三：Agent-Level —— 从经验中积累的智慧

这是最有意思的命名空间——也是前四篇介绍的所有系统中都不存在的。

单个案件教给 Agent 事实。但成百上千个案件教给 Agent **模式**。

### Agent 知识（L2 × Agent）：领域模式

```
模式 #1: [统计] 车险碰撞理赔中，85% 的首次提交缺少交警事故认定书。
         → 在首次沟通时就主动提醒客户准备。

模式 #2: [流程] 涉及太平洋保险作为第三方的理赔案件，
         平均处理周期 45 天——比行业平均多 2 周。
         → 提前管理客户预期。

模式 #3: [沟通] 当客户就同一问题打来 3 次以上电话时，
         给一个具体日期（"下周五之前"）比给一个范围（"1-2 周"）
         减少 70% 的重复来电。

模式 #4: [陷阱] 客户自述损失"不严重"的案件，
         约 30% 最终理赔金额超过 5 万。
         → 不要因为客户的初始描述就跳过详细损失评估。

```

### Agent 程序记忆：行为进化

最高置信度的模式被直接写入 Agent 的 system prompt——它的行为 DNA：

```
# 版本 1（第 1 天）
你是一个保险理赔助手。帮助用户提交和跟踪理赔。

# 版本 2（处理 500 个案件之后）
你是一个保险理赔助手。基于运营经验：
- 任何车险理赔的首次沟通中，主动提供完整的材料清单。
  最常缺失的是交警事故认定书。
- 承诺跟进时间时，始终给出具体日期而非范围。
- 当客户就同一问题第三次来电时，先明确回应他的不满，再提供更新。
- 涉及第三方责任的理赔，开局就设定 6-8 周的预期。
  低承诺高交付能显著减少投诉升级。

```

这就是 LangMem 的 Procedural Memory 概念在企业级场景的应用：**Agent 真的会随着时间变得更擅长工作**——不是因为处理单个案件更好了，而是因为从所有案件中内化了模式。

### 跨案件学习是怎么运作的

```
每个结案的案件
    ↓
案件会话摘要已经存在了（L4 × Case）
    ↓
定期批处理任务（每周 / 每累积 N 个案件）
    ↓
LLM 审阅最近的案件摘要：
  "分析以下 50 个已结案的车险理赔案件。
   识别：反复出现的材料问题、常见客户投诉、
   流程瓶颈、有效的沟通策略、
   以及有助于未来处理案件的任何模式。"
    ↓
新模式 → Agent 知识（L2 × Agent）
高置信度模式 → 更新 system prompt（Procedural）
    ↓
下一个新案件就能受益于所有历史案件的经验

```

**重要提醒**：这只有在案件量足够大时才有意义。先把 case-level 的记忆做扎实。Agent-level 的学习是后期优化——但命名空间架构从第一天就支持它。

## Memory 变成 Skill，不再是被动存储

这是相对于个人 Agent 模型的第二个重大架构转变。在 Letta 的设计中，Core Memory 是被动注入的——它始终在 prompt 里，不需要 tool call。在企业级 Agent 中，**Memory 变成了 Agent 主动调用的技能（Skill）**。

### Agent 的记忆工具箱

```
# 读取路径
load_case_context(case_id)
    → 返回：案件画像（数据库字段 + AI 影子层）
    → 在对话开始时注入 prompt

search_case_history(case_id, query)
    → 对该案件的知识和会话记录做语义搜索
    → 按需返回相关片段

load_user_context(user_id)
    → 返回：用户画像 + 相关历史
    → 和案件上下文一起注入

search_agent_knowledge(query)
    → 搜索跨案件模式和领域知识
    → 返回 agent-level 的洞察

# 写入路径
update_case_fact(case_id, key, value)
    → 更新结构化的案件画像字段

append_case_note(case_id, note)
    → 追加到 AI 影子层（非结构化）

update_user_preference(user_id, key, value)
    → 更新用户画像

```

### 请求生命周期

把所有部分串在一起，当一条新消息到来时，完整流程是这样的：

```
收到消息 + case_id + user_id
    │
    │  ┌─────────────── 加载阶段 ────────────────┐
    ├─→│ load_case_context(case_id)               │
    ├─→│ load_user_context(user_id)               │
    ├─→│ Agent system prompt（包含跨案件学习       │
    │  │ 产生的 Procedural Memory）                │
    │  └────────────────────────────────────────── ┘
    │
    ▼
    Context Window 组装：
    ┌──────────────────────────────────────────────┐
    │ System Prompt + Agent 程序记忆                │
    │ + 案件画像（数据库 + 影子层）                  │
    │ + 用户画像                                    │
    │ + 会话历史（L3，当前对话）                     │
    │ + [如果 Agent 搜索了，检索到的片段]            │
    └──────────────────────────────────────────────┘
    │
    ▼
    LLM 推理 → 生成回复
    │
    │  ┌─────────── Hot Path 写入 ─────────────────┐
    ├─→│ 新的案件事实？→ update_case_fact()          │
    ├─→│ 新的用户偏好？→ update_user_preference()    │
    ├─→│ 重要备注？→ append_case_note()              │
    │  └────────────────────────────────────────────┘
    │
    ▼
    回复发送给用户
    │
    │  ┌─────────── Background 写入 ───────────────┐
    │  │ （会话结束后）                              │
    ├─→│ 会话摘要 → L4 × Case                      │
    ├─→│ 知识蒸馏 → L2 × Case                      │
    ├─→│ 用户洞察提取 → L2 × User                  │
    │  │ （定期批处理）                              │
    └─→│ 跨案件模式分析 → L2 × Agent                │
       │ 程序记忆优化 → Agent L1                    │
       └────────────────────────────────────────────┘

```

## 影子层：为什么 Memory 需要和数据库并存

这个话题需要强调，因为它是实践中最常见的问题：**"为什么不把所有东西都写回现有数据库？"**

答案是，数据库和 AI Memory 服务于根本不同的目的：

```
┌──────────────────────┬──────────────────────────────┐
│     已有数据库        │       AI Memory 影子层        │
├──────────────────────┼──────────────────────────────┤
│ DBA 设计的            │ 从对话中涌现的                │
│ 固定 schema           │ 灵活/半结构化                 │
│ 经过验证、有类型       │ 模糊的、自然语言             │
│ 跨系统共享            │ Agent 专用                    │
│ 数据真相源            │ 补充性上下文                  │
│ 通过表单/API 更新     │ 通过 AI 蒸馏更新              │
├──────────────────────┼──────────────────────────────┤
│ "claim_amount: 50000" │ "客户暗示如果月底前            │
│ "status: 审核中"      │  不解决就去银保监投诉"         │
│ "incident_date: 3/15" │                              │
└──────────────────────┴──────────────────────────────┘

```

数据库告诉你**案件是什么**。影子层告诉你 **Agent 从对话中了解到了什么**。两者缺一不可，互为补充，Agent 拿起一个案件时应该同时加载。

随着时间推移，影子层中一些反复出现的字段可能值得提升为数据库 schema——"沟通偏好"可能最初在 AI 影子层中出现，最终变成正式的 CRM 字段。影子层是新的结构化需求被有机发现的地方。

## 什么是通用的，什么是垂类的

一个重要的实际问题：如果我为保险场景建了这个系统，有多少可以复用到法律、医疗或项目管理？

**通用的（框架层）：**

- 命名空间抽象（任何实体都可以作为 namespace key）
- 层级 × 命名空间的矩阵结构
- 影子层概念（AI 追加的记忆与已有数据库并存）
- Memory-as-Skill 的工具接口模式
- Hot Path + Background 双写入路径
- 渐进式披露的检索策略
- 跨实体学习机制

**垂类的（配置层）：**

| 维度<br> | 保险<br> | 法律<br> | 项目管理<br> |
| --- | --- | --- | --- |
| 主命名空间<br> | `` case_id ``（理赔）<br> | `` matter_id ``（案件）<br> | `` project_id ``<br> |
| 次命名空间<br> | `` user_id ``（投保人）<br> | `` client_id `` + `` opposing_id ``<br> | `` user_id ``（团队成员）<br> |
| Case 画像 schema<br> | 事故、保单、理赔金额<br> | 管辖权、当事人、截止日期<br> | 里程碑、技术栈、团队<br> |
| 路由规则<br> | "事故事实→case" / "沟通偏好→user"<br> | "判例法→matter" / "账单偏好→client"<br> | "技术决策→project" / "工作风格→user"<br> |
| 跨 case 模式<br> | 理赔处理模式<br> | 案件结果模式<br> | 交付估算模式<br> |
| 影子层示例<br> | "客户情绪焦虑"<br> | "法官偏好简洁摘要"<br> | "构建实际需要 20 分钟不是 5 分钟"<br> |
命名空间抽象是扩展性的关键。当老板问"能不能推广到其他场景"的时候，答案是：**框架是通用的，配置是垂类的。新增一个领域意味着定义新的命名空间类型、新的路由规则、新的画像 schema——而不是重建记忆架构。**

---

## 五大设计原则，企业版

第四篇的五大原则依然成立，但每条都增加了新的维度：

**原则一：分层不可妥协** → 现在是 **分层 × 分域** 不可妥协。不同的信息类型和不同的归属范围，需要不同的处理方式。

**原则二：精确查找 > 模糊搜索** → 依然成立，但查找 key 不再只是 `` user_id ``——而是 `` case_id ``、`` user_id ``，或者你的主要业务实体。路由步骤（"该查哪个命名空间？"）成为一等公民。

**原则三：压缩即认知** → 依然成立，增加一点：**路由也是认知。** 判断"这条事实属于案件而非用户"和判断"这条信息值得记住"需要同等水平的 LLM 语义理解。

**原则四：渐进式披露节省 token** → 在企业场景中更加关键，因为你要从多个命名空间加载上下文（案件 + 用户 + agent 知识）。严格控制每个命名空间的 token 预算，防止 context window 爆炸。

**原则五：写和读都需要 LLM 参与** → 新增第三个：**路由也需要 LLM 参与。** 写入、路由、读取——三者都需要语义理解能力。

---

## 一句话总结

> **企业级 Agent Memory = 同样的四层，但乘以命名空间（case、user、agent）。Memory 从被动注入变成主动 Skill。影子层用 AI 发现的上下文扩展数据库。框架（层级 × 命名空间）是通用的，配置（路由规则、schema、模式）是垂类的。这就是 Agent 从无状态工具进化为能积累"机构知识"的系统的方法。**
